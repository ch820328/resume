# Power Story 02: Secure Python EFI (Security Enforcement)
## 核心主題：專案卡住 (Project Stuck)、決策權衡 (Trade-off)、風險管理、Leadership

### 🚀 STAR Story

#### **1. 結論先行 (High-level Impact)**
在發生離職員工盜取生產診斷工具的資安事件後，公司核心 IP 面臨巨大威脅。我 **主動發起並實作了「Secure Python EFI」方案**。透過修改 **`PyImport_ImportModule`** 核心函數，我實作了 RSA 非對稱加密的執行環境。這在不影響開發效率的前提下，為公司 IP 建立了物理級的保護牆，成功防止了診斷邏輯的外洩。

#### **2. 分層解決方案 (Tier - Architecture)**
為了在受限的 EFI 環境中實作安全，我將方案分為三層：
*   **金鑰管理層 (Server Side)**：私鑰僅存在於受控的安全伺服器，由維護者在伺服器端完成加密，確保開發者機器不留存敏感金鑰。
*   **直譯器核心層 (Modified Runtime)**：修改 `python.efi` 的 C 源碼，在模組載入階段插入解密鉤子。
*   **執行層 (In-Memory Execution)**：代碼全程不落地，僅在授權的記憶體空間內解密執行，徹底杜絕了反向編譯的可能。

#### **3. 關鍵決策與 Leadership (Layer - Decision & Risk)**
*   **專案卡住時的決策 (Stuck & Trade-off)**：事件發生後，團隊曾考慮將所有邏輯重寫為 C++ 以保證安全。但我分析後發現，硬體驗證邏輯變動極快，C++ 的開發成本會讓產線停擺數週。**我主動建議並推動「修改 Python 運行時」**。這是一個「高難度但高效益」的決策：我們保留了 Python 的迭代速度，同時透過 RSA 強制加密獲得了與二進位檔案同等的保護力。
*   **風險管理 (Risk Management)**：在動手修改編譯器核心前，我預見到 EFI 環境記憶體極度受限的風險。我沒有直接實作 RSA 全解密，而是採取了 **「混合加密策略 (AES + RSA)」**：用 RSA 保護 AES 金鑰，用高效的 AES 解密 Payload。這保證了在不增加啟動延遲的情況下，完成複雜的解密流程。
*   **展現 Ownership (我觀察到...我決定...)**：我觀察到原本的 `.pyc` 檔案非常容易被解鎖，這不只是單個 Bug，而是架構漏洞。我決定不採取「混淆 (Obfuscation)」這種治標不治本的方法，而是從直譯器底層進行技術強制 (Technical Enforcement)。

#### **4. 結果與成果 (Result)**
*   **結果**：成功建立 IP 保護屏障，並將其標準化為部門所有 EFI 工具的必備框架。
*   **影響力**：這種「預防性安全」的設計，讓公司在後續的專案合作中，能放心地將診斷工具交給協力廠商使用，而不用擔心邏輯外洩。
