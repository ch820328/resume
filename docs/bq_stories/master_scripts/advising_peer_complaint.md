**題目：如果團隊成員抱怨另一位同事的行為，你會如何給建議？**

**回答：**
我處理此類投訴的原則是 **「不選邊站，將情緒轉化為事實，並鼓勵直接且建設性的溝通」**。

在推動 **RFTool** 期間，曾有一位隊友私下向我抱怨另一位同事「工作不負責任」，因為對方頻繁修改底層介面卻不告知，導致他的測試腳本一直壞掉。這讓他感到非常沮喪。

我採取了以下建議方式：
1.  **傾聽並引導至事實 (De-escalation)**：我首先讓他完整表達挫折感，但我不參與對另一人的性格評價。我引導他將「他不負責任」這種指控，轉化為「介面變動沒通知」這個具體的 **技術行為問題**。
2.  **指導 SBI 回饋模型 (Coaching SBI Model)**：我建議他直接與對方進行 1-on-1，並指導他使用 **SBI 模型 (Situation, Behavior, Impact)**。我告訴他：「與其指責對方，不如陳述事實：『在昨天的 PR 中 (S)，當你修改了函式名稱卻沒在群組通知時 (B)，導致我花了數小時修復回歸錯誤 (I)。』」
3.  **提供系統性的解決方案**：我告訴他，如果直接溝通後仍無改善，我願意主持一個三方會議來建立團隊的 **「變更通知規範 (Change Notification SOP)」**。
4.  **技術面的防禦**：我也建議他在架構中加入「過時警告 (Deprecation Warning)」，從技術層面降低「人為疏忽」帶來的溝通成本。

**結果**：
這位隊友採納了我的建議與對方溝通，兩人在私下達成了共識。後來我們也順勢建立了團隊的 **API 變更規範**。這次經驗讓我體會到，處理團隊摩擦最好的方式不是當法官，而是 **「給予成員解決問題的工具與勇氣」**，將人際衝突轉化為流程優化的動力。
