**題目：描述一次你在工作中處理衝突的經驗。**

**回答：**
處理衝突時，我習慣將 **「人的情緒」與「技術事實」拆開來處理**。

在推動 **RFTool (物件導向框架)** 時，我與一位資深工程師發生了嚴重的技術衝突。他堅持要維持舊有的「平鋪式腳本」寫法，認為 OO 框架太過抽象且難以除錯；而我則堅持為了長期的可重用性，必須建立 Base Class。

我的處理方式是：
1.  **先處理情緒 (Listen First)**：我發現他之所以強烈反對，是因為他擔心這套新框架會讓他原本寫好的幾十個舊腳本作廢。我第一時間向他保證：「我們會寫適配器 (Adapter) 確保舊腳本能跑，不會讓你白費功夫。」
2.  **用數據說話 (Evidence-based)**：我沒有跟他爭論理論，我直接用了半天的時間，用新框架重寫了他最複雜的一個腳本。我展示給他看：原本 500 行的代碼，現在只要繼承 Base Class，核心邏輯只要 50 行就能完成。
3.  **尋找技術平衡點**：我邀請他參與 Base Class 的設計，讓他把擔心的「效能瓶頸」部分加入審核。

**結果：**
當他親眼看到開發效率提升了數倍，且他的專業意見被採納後，他成了團隊裡最支持這套框架的人。這次經驗讓我學到，解決衝突最好的方式不是說服對方你是對的，而是 **「用對方的成功來證明你的方案是有價值的」**。
